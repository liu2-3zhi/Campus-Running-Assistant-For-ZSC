# 多账号全部停止修复（2026-11-23）

## 故障原因

“全部开始”和“启动选中”会逐个启动账号。“全部停止”只设置停止事件，没有取消尚未执行的启动队列。后续账号启动时又清除停止事件，导致停止后仍继续启动账号。

后端还会在全局停止标记已置位时直接返回成功，未确保每个账号都收到停止信号。旧版按钮的禁用状态仅统计有可执行任务摘要的账号，登录中或收尾中的真实工作线程可能被漏掉。

## 修复行为

- 前端停止操作立即使尚在预检、启动延迟或上一启动请求中的旧队列失效，桌面和移动端共用取消状态。
- 已发出的启动请求可能晚于停止请求到达后端，因此停止操作还会等待这些在途启动请求结束后补发停止，期间阻止新的启动操作越过停止流程。
- 后端以停止序号识别停止前发起的启动请求，在同一执行锁下检查序号并占用账号执行槽，防止取消标记被旧启动清除。
- 全部停止始终通知各账号，并刷新停止状态；按钮可用性依据真实活动线程，不能因任务摘要为空而禁用停止。
- 新的主动启动操作可以在停止后正常开始。旧版移动端在停止请求失败时显示错误。

正在进行的外部请求仍需返回；取消信号确保其完成后不再继续生成或提交任务。

## 任务间等待时开始

账号显示“任务间等待”时，再次点击该账号的“开始”会唤醒原工作线程，立即执行已经选好的下一任务。每次等待使用独立事件，退出等待后清除引用；一次点击不能跳过后续任务间隔。正在正常执行任务时仍不允许创建第二线程，停止请求优先于跳过等待。

状态快照和状态推送携带 `can_skip_wait`，供桌面、移动端及展开列表的开始操作识别当前等待。续跑沿用本次任务执行状态，不重新消费启动预检或计费豁免选项。

新增回归使用真实账号工作线程覆盖等待唤醒、线程不重复、下一间隔保持等待、停止优先以及状态快照/推送。此前全量结果对应“全部停止”修复；本节续跑改动另行执行相关回归。
