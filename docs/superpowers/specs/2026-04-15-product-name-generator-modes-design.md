# 商品名生成器行业模式扩展设计

- 日期：2026-04-15
- 主题：为 `product_name_generator.py` 增加可切换的行业模式，并在 `main.py` 启动前加入模式校验
- 状态：待评审

## 1. 背景与问题

当前 `product_name_generator.py` 只支持“现卤现捞”这一套商品名生成逻辑，类名为 `LoMeiGenerator`，内部词库、模板、兜底文案也都与餐饮场景强绑定。

这带来两个问题：

1. 无法直接支持新的行业场景，例如旅行社 / 旅游服务行业的收费项名称。
2. 生成器当前没有显式的行业模式配置与启动校验，若后续通过手改代码切换场景，容易误写、误切换，且错误只能在运行期暴露。

用户已确认本次新增的行业方向为“旅游服务行业模式”，但实际命名风格不是宣传型套餐，而是更接近业务收费项，例如：

- `资料打印费`
- `短信费`

同时，数量需要体现在名称前缀中，并配合项目自己的固定量词，例如：

- `三份资料打印费`
- `二次短信费`

## 2. 设计目标

1. 在 `product_name_generator.py` 中增加一个文件顶部模式变量，用于切换当前行业模式。
2. 保持现有“现卤现捞”模式行为兼容，不影响已有支付商品名生成逻辑。
3. 新增“旅游服务”模式，支持生成类似“二次短信费”“三份资料打印费”的收费项名称。
4. 在 `main.py` 启动前增加模式配置校验，配置错误时直接阻止启动并给出明确提示。
5. 设计上保留可扩展性，使后续增加更多行业模式时，尽量只补配置，不重写主流程。
6. 增加足够清晰的注释，降低误切换风险。

## 3. 非目标

1. 本次不重命名 `LoMeiGenerator` 类，也不重构为多文件多类架构。
2. 本次不新增后台管理页面或环境变量配置入口，模式切换仍通过 `product_name_generator.py` 顶部常量完成。
3. 本次不引入复杂的行业规则引擎，仅在现有生成器上扩展统一的模式配置结构。

## 4. 方案选择

本次采用用户确认的 **方案 1：单文件顶部常量切换 + 同类内多模式配置**。

### 4.1 备选方案对比

**方案 1：单文件顶部常量切换 + 同类内多模式配置**
- 优点：改动最小，兼容现有调用方式，最符合“新增一个变量切换模式”的需求。
- 缺点：`LoMeiGenerator` 类名与行业泛化后的职责不完全一致，但短期可接受。

**方案 2：新增通用生成器包装层**
- 优点：命名更中性，后续扩展更自然。
- 缺点：改动范围扩大，需要调整调用点，本次需求下偏重。

**方案 3：每个行业独立生成器类**
- 优点：边界清晰，长期扩展性最好。
- 缺点：实现成本高，不符合本次“在原文件中新增模式切换”的要求。

### 4.2 最终选择理由

选择方案 1，同时在实现细节上引入“模式配置表”来保证可扩展性。这样可以在维持低改动量的前提下，避免后续逻辑演变成散乱的 `if mode == ...` 分支堆积。

## 5. 详细设计

### 5.1 `product_name_generator.py` 顶部新增模式常量

在文件顶部新增如下概念：

- 全局模式常量：`PRODUCT_NAME_GENERATOR_MODE`
- 允许值集合：由统一模式配置表决定，例如：`lomei`、`travel_service`

注释要求：

1. 明确说明这是“全局行业模式开关”。
2. 明确说明不得随意切换，切换前应确认当前站点业务场景。
3. 明确列出允许值来源于模式配置表，禁止手写未注册值。
4. 说明新增行业时，应先补充模式配置，再修改模式常量。

这样可以把“误切换”风险收敛到配置层，并通过注释降低维护误操作概率。

### 5.2 引入统一模式配置表，提升可扩展性

为了支持未来扩展，不直接把每个行业写成零散条件分支，而是在模块内引入统一模式配置表，例如概念上包含：

- `display_name`：模式中文名，便于报错与注释
- `fallback_name`：兜底商品名模板
- `builders` 或 `strategy_type`：该模式使用的生成策略入口
- `items` / `foods`：基础项目词库
- `quantifiers` 或 `item_quantifier_map`：量词配置
- `adj_flavor` / `adj_emotion` / `connectors`：适用于该模式的修饰词与连接词

其中：

- `lomei` 模式继续使用现有餐饮词库与分拆逻辑。
- `travel_service` 模式使用收费项词库与固定量词映射。

模式校验、模式加载、错误提示都统一基于这个配置表完成。这样后续新增 `property_service`、`education_service`、`tech_service` 等模式时，只需新增一条配置并按统一接口接入。

### 5.3 生成器内部结构调整

保留 `LoMeiGenerator` 类作为外部兼容入口，但内部改为“按模式加载配置”。

建议调整为以下职责划分：

1. **模式读取与校验**
   - 初始化时读取 `PRODUCT_NAME_GENERATOR_MODE`
   - 若模式不存在，则抛出明确异常

2. **模式配置加载**
   - 根据模式选择对应配置
   - 将当前模式所需词库、量词规则、连接词、兜底文案载入实例属性

3. **公共能力复用**
   - 中文数字转换 `_int_to_chinese`
   - UTF-8 字节长度计算 `_get_byte_len`
   - 数量分拆 `_partition_integer`

4. **模式专属生成逻辑**
   - `lomei`：沿用现有趣味描述策略
   - `travel_service`：走收费项风格策略

这样可以做到“公共能力共享，模式逻辑隔离”，避免每新增一个行业就复制整套基础工具函数。

### 5.4 `travel_service` 模式设计

#### 5.4.1 命名目标

`travel_service` 模式生成结果应偏“收费项目名”，而不是营销套餐名。命名风格要求简洁、稳定、可读，适合作为支付商品名。

示例目标：

- `一份资料打印费`
- `二次短信费`

#### 5.4.2 数据结构

该模式建议使用“项目绑定固定量词”的结构，例如概念上：

```python
travel_service_items = [
    {"name": "资料打印费", "quantifier": "份"},
    {"name": "短信费", "quantifier": "次"},
]
```

这样量词与项目绑定，避免随机量词带来不自然结果，例如“二根短信费”之类错误组合。

#### 5.4.3 生成规则

1. 数量统一转中文数字。
2. 名称格式统一为：`中文数字 + 固定量词 + 项目名`
3. 默认不引入情感词、夸张修饰词和复杂连接句，保持收费项风格稳定。
4. 若未来扩展更多旅游服务收费项，只需新增项目及对应量词映射。

#### 5.4.4 兜底策略

若多次尝试后仍未生成合规名称，则使用该模式的兜底文案模板，例如：

- `X项旅游服务费`

其中 `X` 仍使用中文数字。

### 5.5 `lomei` 模式兼容策略

现有现卤现捞逻辑原则上保持不变，包括：

- 食材库
- 量词库
- 风味形容词
- 情感形容词
- 连接词
- 分拆与拼接策略
- 127 字节限制控制
- 兜底文案

允许做的仅是结构性整理，例如把现有词库放入 `lomei` 模式配置中，但不能改变默认生成语义。

### 5.6 模式校验函数设计

在 `product_name_generator.py` 中新增公共校验函数，例如语义上：

- `validate_product_name_generator_mode(mode=None)`
- `get_supported_product_name_generator_modes()`

设计要求：

1. `mode` 为空时，默认校验当前全局模式常量。
2. 若模式非法，抛出 `ValueError`。
3. 错误信息包含：
   - 当前非法值
   - 允许值列表
   - 提示应在模式配置表中注册后再使用

这样 `main.py` 与模块内部都可以复用同一套校验逻辑，避免重复维护两份允许值判断。

### 5.7 `main.py` 启动前校验设计

#### 5.7.1 目标

在应用进一步启动前就发现模式配置错误，避免在支付流程触发商品名生成时才暴露异常。

#### 5.7.2 实现位置

在 `main.py` 的启动入口中、实际启动服务之前执行一次校验。可接受的实现方式包括：

1. 在 `main()` 早期阶段导入 `PRODUCT_NAME_GENERATOR_MODE` 与校验函数并执行。
2. 或在模块初始化完成、服务启动前的集中校验流程里执行。

无论具体放在哪个初始化节点，都必须满足：

- 若模式非法，程序直接中止启动。
- 日志或控制台输出明确错误信息。
- 报错包含当前值与允许值。

#### 5.7.3 错误表现

示例错误语义：

- 当前配置值无效：`PRODUCT_NAME_GENERATOR_MODE='xxx'`
- 允许值：`lomei`, `travel_service`
- 请先在 `product_name_generator.py` 的模式配置表中注册后再切换

### 5.8 对现有调用点的兼容性

当前 `main.py` 中已有：

- `generator = LoMeiGenerator()`
- `product_name = generator.generate(quantity)`

本次保持这套调用方式不变。切换行业模式后，调用方无需改造参数，只通过模块顶部常量改变生成行为。

这保证了本次需求能以最小代价接入现有支付流程。

## 6. 测试设计

### 6.1 生成器测试点

1. `lomei` 模式下仍能生成现有风格名称。
2. `travel_service` 模式下能生成 `中文数字 + 固定量词 + 项目名` 格式。
3. `travel_service` 模式中：
   - `资料打印费` 使用固定量词 `份`
   - `短信费` 使用固定量词 `次`
4. 非法数量（非整数、<=0）仍返回 `None`。
5. 生成结果仍满足 127 字节限制。
6. 兜底文案按模式分别生效。

### 6.2 模式校验测试点

1. `lomei` 为合法值。
2. `travel_service` 为合法值。
3. 未注册模式值会抛出明确 `ValueError`。
4. 错误信息中包含非法值与允许值列表。

### 6.3 启动前校验测试点

1. 模式合法时，`main.py` 可继续启动。
2. 模式非法时，`main.py` 在服务启动前即失败退出。
3. 错误日志中包含定位信息，不需要等到支付接口调用时才发现问题。

## 7. 受影响文件

- `product_name_generator.py`
  - 新增全局模式常量
  - 新增统一模式配置表
  - 新增模式校验函数
  - 扩展生成器以支持 `travel_service`
- `main.py`
  - 新增启动前模式校验
  - 视需要优化非法模式的日志输出

## 8. 风险与缓解

### 8.1 风险：类名与职责不完全匹配

`LoMeiGenerator` 名称仍偏餐饮语义，但实际已支持多行业。

**缓解：** 本次保持兼容，后续若行业继续扩张，再单独评估是否引入更中性的生成器入口。

### 8.2 风险：未来新增模式时又回到散乱条件分支

如果后续直接在方法里追加大量 `if/elif`，可扩展性会退化。

**缓解：** 本次明确使用统一模式配置表，并让校验逻辑与允许值列表都基于该配置表生成。

### 8.3 风险：误切换模式导致线上命名风格突变

**缓解：**
- 在顶部常量上增加醒目注释
- 在启动前强制校验
- 错误配置直接阻止启动

## 9. 验收标准

1. `product_name_generator.py` 顶部存在明确的模式常量与防误切换注释。
2. 默认 `lomei` 模式继续正常生成现卤现捞风格商品名。
3. 新增 `travel_service` 模式后，可生成类似 `三份资料打印费`、`二次短信费` 的名称。
4. `travel_service` 模式使用项目固定量词，而不是随机量词。
5. 模式校验基于统一配置表实现，而不是把允许值分散写在多个位置。
6. `main.py` 在应用启动前执行模式校验；若模式非法，程序直接失败并给出明确提示。
7. 后续新增行业模式时，主要通过补充模式配置表即可完成接入。
