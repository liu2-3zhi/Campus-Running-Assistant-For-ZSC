# UUID 绑定优先与登录按钮误刷新修复设计

- 日期：2026-04-11
- 主题：默认主题背景在 UUID 初始化与 PC 登录点击场景下的绑定优先与防误刷新修复
- 状态：待评审

## 1. 背景与问题

当前默认主题随机背景在两个场景下仍不符合预期：

1. **带 UUID 初始化时仍随机图覆盖绑定图**
   - 用户访问带 `uuid` 的 URL 时，并不代表一定存在有效绑定，因为绑定可能已经过期。
   - 正确规则应为：**如果该 UUID 对应 target 存在未过期绑定，则优先返回绑定背景；否则返回随机背景。**
   - 现状是在初始化后的主题同步过程中，仍可能再次拿到随机图并覆盖已绑定结果。

2. **PC 端点击 `auth-login-btn` 会误触发背景刷新**
   - 点击 PC 登录按钮时，背景图片本身已经加载完成，但登录流程中的主题同步/背景消费链路会再次改写登录页背景。
   - 这会让用户看到“点击按钮就换图”的错误体验。

## 2. 设计目标

1. 带 `uuid` 初始化时严格遵循：**有有效绑定则复用，无绑定或过期则随机。**
2. 修复 PC 端点击 `auth-login-btn` 时的误刷新问题。
3. 保持现有“登录前快照参与绑定”的能力，不破坏之前已确认的登录前背景继承逻辑。
4. 改动尽量收敛：以后端为主判定，前端只做必要防覆盖保护。

## 3. 方案选择

采用已确认的 **方案 1：后端优先判定 + 前端点击防误刷新保护**。

### 3.1 后端主导

由后端在生成主题配置时直接决定该次请求返回：

- 绑定图（如果存在且未过期）
- 随机图（如果不存在绑定或绑定已过期）

这样前端初始化拿到的就是“正确背景”，不需要靠后续补偿逻辑纠正。

### 3.2 前端补充保护

前端保留现有背景消费与绑定上报机制，但在 **PC 登录按钮点击 → 登录成功 → 主题同步** 这一链路上增加保护：

- 点击登录时不应把当前背景当成“需要重新随机/重新覆盖”的新候选。
- 登录成功后的主题同步如果返回的仍是当前绑定图，则只应用一次，不制造视觉刷新。
- 若后端返回的是绑定失效后的新随机图，则允许更新，但不能因为前端重复触发链路而出现多次切换。

## 4. 根因判断

### 4.1 初始化问题根因

当前初始化链路中，前端在加载初始数据后还会执行额外主题同步：

- 初始数据应用：`loadInitialData()` 后应用 `theme_config`
- 后续同步：`syncThemeFromServer(...)`

这使得“第一次拿到的正确背景”有机会在后续同步中被新的默认主题配置覆盖。

### 4.2 登录点击误刷新根因

PC 登录按钮点击后，`handleAuthLogin()` 会先记录登录前背景快照；登录成功后又调用 `syncThemeFromServer(...)`。若该同步重新应用了一个新的 `theme_config`，就会直接重写 `auth-login-container` 的背景样式，形成“点击即换图”的现象。

换句话说，问题不是图片重复加载，而是**背景决策与背景应用被重复执行，并且第二次执行没有优先尊重已绑定结果。**

## 5. 详细设计

### 5.1 后端：主题配置注入时优先检查 UUID 绑定

文件：`main.py`

重点改动在主题配置生成路径：

- `get_theme_config(style_id, targets=None)`
- `_inject_default_theme_background_image(...)`
- 已有绑定工具函数：
  - `_get_session_theme_background_binding(...)`
  - `_resolve_theme_background_binding_decision(...)`

#### 5.1.1 新规则

当请求上下文可获得会话 UUID / URL UUID 对应的会话上下文时：

1. 先按 `(session_uuid, target)` 查绑定。
2. 若绑定存在且未过期：
   - 直接把该绑定图注入 `theme_config`。
   - 不再为该 target 重新选随机图。
3. 若绑定不存在或已过期：
   - 走现有随机背景选择流程。
   - 返回新的随机图。

#### 5.1.2 预期结果

这样可以保证：

- 带 UUID 初始化时，如果绑定有效，前端首屏拿到的就是绑定图。
- 若绑定已失效，则首屏拿到新随机图，符合“过期后随机”的规则。

### 5.2 前端：PC 登录点击链路禁止误刷新

文件：`scripts/main.new.js`

重点关注：

- `handleAuthLogin(...)`
- `syncThemeFromServer(...)`
- `applyThemeLoginContainerStyle(...)`
- `scheduleThemeBackgroundConsumed()` / `notifyThemeBackgroundConsumed(...)`

#### 5.2.1 登录点击阶段

继续保留：

- 点击登录时记录 `preLoginBackgroundSnapshot[target]`

新增约束：

- 点击 `auth-login-btn` 只是记录快照并发起登录，不应触发任何新的背景随机化。
- 登录请求进行中，不应因为按钮状态变化、主题同步或重复应用样式而让 `auth-login-container` 的背景发生额外跳变。

#### 5.2.2 登录成功后的主题同步保护

在 `syncThemeFromServer(...)` 或其后续应用链路中增加幂等保护：

1. 读取当前 PC 登录容器实际渲染背景 URL。
2. 读取本次服务端返回 `theme_config` 中的背景 URL。
3. 若两者相同：
   - 允许更新主题状态缓存；
   - **跳过会引发视觉刷新感知的重复背景写入**。
4. 若两者不同：
   - 仅在后端明确给出了新的有效结果时更新一次。

#### 5.2.3 背景消费上报保护

保留现有 `preLoginBackgroundSnapshot` 与 `candidate_image_url` 机制，但增加一条前端约束：

- PC 登录点击后的这一轮流程中，不能因为同步阶段重复触发 `scheduleThemeBackgroundConsumed()` / `notifyThemeBackgroundConsumed(...)`，把当前已显示背景再次当作新的候选去覆盖。

也就是说：

- **记录快照可以发生；**
- **绑定 ensure 可以发生；**
- **但不能让同一次登录过程出现额外的背景重选和视觉切换。**

## 6. 测试设计

### 6.1 先补失败测试（TDD）

文件：`tests/test_theme_background_binding.py`

新增或扩展以下测试：

1. **有有效绑定时初始化优先返回绑定图**
   - 构造 `(session_uuid, pc)` 未过期绑定。
   - 验证主题配置解析时选中绑定图，而不是新的随机图。

2. **绑定过期时初始化返回随机图**
   - 构造过期绑定。
   - 验证不会继续复用旧绑定，而会选取新的随机图。

3. **登录上下文仍可用登录前快照覆盖旧绑定**
   - 保证不破坏之前已确认的登录前绑定规则。

### 6.2 前端回归验证点

由于当前问题集中在前端登录点击链路，修复后至少要验证：

1. PC 登录页背景已显示时，点击 `auth-login-btn` 不会立刻发生换图。
2. 登录成功后，如果后端返回的是当前绑定图，背景不闪变、不重写成别的随机图。
3. 若绑定已过期，登录或初始化允许切换到新的随机图，但只切换一次。

## 8. 验收标准

1. URL 带 UUID 且绑定有效时，初始化显示绑定图。
2. URL 带 UUID 但绑定不存在或已过期时，初始化显示随机图。
3. PC 端点击 `auth-login-btn` 不会误触发登录页背景刷新。
4. 登录成功后不会因为二次主题同步把当前绑定背景替换成别的随机图。
5. 已有“登录前快照参与绑定”逻辑不回归。

## 9. 非目标

1. 不改动默认主题之外的主题样式逻辑。
2. 不重构整套主题系统。
3. 不新增新的公开 API 路径，优先在现有主题配置与绑定逻辑中修复。
