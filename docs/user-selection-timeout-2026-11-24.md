# 2026-11-24 账号选择导致初始化超时

本轮对照用户新提供的浏览器控制台附件和 `C:\Users\Zelly\Desktop\数据\python_running-new\logs`。运行页面版本为 `20261124-Q7n5LK`，前一轮缓存与日志上传修复已生效；本次剩余故障发生在账号选择路径。

## 证据与根因

浏览器先完成三次 `get_initial_data`，耗时约 9.53、9.65、4.74 秒。11:59:07 发起 `on_user_selected` 并等待“用户上下文初始化”；11:59:37 到达 30 秒期限，随后界面显示“网络错误／服务器无法连接”。

服务端主日志中：

| 日志行 | 时间 | 事件 |
| --- | --- | --- |
| 6155 | 11:59:09 | 收到 `POST /api/on_user_selected` |
| 6159–6164 | 11:59:09 | 更新会话活跃时间、通过 `view_user_details` 权限、进入账号选择处理 |
| 6208–6670 | 11:59:13–12:00:08 | 同一请求逐个加载 446 个账号的统计配置 |
| 6671 | 12:00:08 | 完成自有 446 账号加载 |
| 6672–6673 | 12:00:08 | 继续检查管理员全量聚合权限；快照到此结束，尚无该请求完成记录 |
| 6481–6484 | 11:59:42 | 收到前端超时日志；日志上传本身正常返回 200 |

因此，请求实际抵达且鉴权通过。选中一个账号只需其密码、UA 和现有参数，原实现却调用 `_load_user_school_accounts()`，先读取全部自有账号统计，再进行管理员聚合，导致串行数据库读取超过前端期限。日志没有 SQL 分段耗时，无法精确拆分每条查询耗时。

此外，`onUserChange()` 在单账号接口成功后还等待 `/auth/get_user_school_accounts`。该接口也会读取全部账号和统计，即使修复第一处，第二次全量读取仍可能拖住同一个初始化阶段。

`initializeApp()` 的统一异常处理没有区分超时与断网，将所有异常固定展示为“服务器无法连接”。本次报错时日志接口正常响应，并非服务器整体不可达。11:58:16 的另一次账号选择 401 属于更早的无会话阶段，与本次已通过鉴权的请求不同。

## 修复

- 新增单账号凭据读取：自有绑定命中后立即返回，不读取统计、不扫描其他 owner。
- 管理员跨 owner 读取仍要求原有 `manage_users` 权限；只查目标账号，保留当前 owner 优先、旧字符串密码及目标 INI 兼容。数据库模式下批量读取绑定，避免逐文档往返。
- 密码 `own` 可见性检查复用单账号的 `own_only` 读取；兼容前端数组参数和对象参数，未关联账号仍不下发密码。
- 前端删除成功后重复的全量账号请求，只采用已过滤的单账号响应，保持密码清空和桌面／移动端 UA 同步。
- “仅查看本人账号”的初始数据分支只读取该 owner 的合法账号名称，不再为获取名称而加载全部统计；数据库错误仍返回初始化失败，不会伪装成空列表成功。
- 初始化超时显示具体阶段的“初始化超时”；程序异常显示“初始化失败”；真实 fetch 连接失败继续显示“网络错误”。保留原有 30 秒超时。
- 前端版本更新为 `20261124-R8m2VN`。
